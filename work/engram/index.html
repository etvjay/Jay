Engram

Execution-memory infrastructure for testing whether prior experience actually changes a later autonomous decision.

I built Engram around a stricter definition of memory: retrieval is not enough. A prior execution only becomes operational memory when it is recalled under comparable conditions, explicitly influences a later decision, changes the action relative to a memory-free control, and leaves enough provenance to reconstruct what happened.

01 / Problem

Most agent “memory” systems prove retrieval, not influence.

A memory that appears in a prompt has not yet been shown to matter.

Engram asks a narrower systems question: when can we truthfully say that a previous execution changed what an autonomous system did later?

The project treats that claim as something that should be reconstructable from execution evidence rather than inferred from a successful outcome.

02 / Model

Memory is modeled as a causal relationship between two executions.

source execution
      │
      ▼
operational memory
      │
      ▼
comparable future recall
      │
      ▼
application decision references memory
      │
      ▼
action differs from memory-free control
      │
      ▼
outcome observed + provenance retained

Engram does not become the decision authority. The application or agent still chooses the business action.

Episode

Versioned execution record carrying intent, decisions, observations and outcome.

Operational memory

A lesson admitted from prior execution evidence under explicit policy.

Recall

Comparable prior experience retrieved for a future execution.

Influence

An explicit reference from the later decision to the memory that affected it.

Counterfactual

The memory-free control used to test whether the later action actually changed.

03 / What I built

The project spans protocol semantics, runtime behavior, persistence and integration surfaces.

Execution protocol

Versioned ExecutionEpisode model with decisions, observations, outcomes and provenance.

Memory runtime

Admission, eligibility, recall, influence, expiry and invalidation semantics.

Persistence

CockroachDB-backed execution, memory, vector and evaluation state with agent-scoped retrieval.

SDK / API / MCP

TypeScript and Python clients, HTTP routes and semantic MCP surfaces for inspecting execution memory.

Adapters

Integration surfaces for OpenAI Agents, LangGraph and custom agent runtimes.

Evaluation

Governed experiments for changed action, stale memory, competing memories and provenance mismatch.

04 / Technical decision

Memory remains subordinate to present authority.

Engram may surface prior experience; it does not silently turn past behavior into a new permission.

context
   │
   ▼
recall candidate
   │
   ▼
policy / eligibility check
   │
   ├── blocked → no exposure / no influence
   │
   └── allowed
          │
          ▼
application decides
          │
          ▼
authorize → execute → observe

This matters for stale or incompatible memory: retrieval can succeed while influence is still denied. Contradictory memories can also remain visible without the memory layer implicitly adjudicating between them.

06 / Boundary

Cloud integration claims remain separate from implementation claims.

The external demo workload is simulated. Live CockroachDB Cloud persistence, Bedrock Titan invocation, Managed MCP provenance, natural C-SPANN index selection and AWS public deployment remain unverified until their credentialed proof paths succeed.

The repository explicitly distinguishes those states rather than treating integration code or skipped credential-gated tests as external verification.
