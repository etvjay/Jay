OpenRails

A coordination and settlement system for turning bounded commercial authority into verifiable payment outcomes.

I built OpenRails around a simple separation: agreement, authority, proof and settlement should remain connected without becoming the same thing. The system carries a commercial relationship from persistent context through bounded delegation, accepted terms and evidence into direct or streamed USDC settlement.

01 / Problem

Most payment systems remember the transfer better than the relationship that authorized it.

OpenRails asks what should exist between an agreement and a transaction.

A commercial payment often depends on more than sender, recipient and amount. It may depend on who is allowed to act, under which limits, against which accepted terms, after what evidence, and with what record afterward.

The project began by treating those pieces as one lifecycle while keeping their authority boundaries distinct.

The Runtime governs coordination state. The Arc Hub/Vault remains the financial settlement boundary.

Workspace

Persistent context for the commercial relationship and its participating actors.

Path

Repeatable delegated authority with explicit limits rather than unrestricted custody.

Pact

The point where accepted terms become a committed relationship state.

Proof

Evidence associated with the Pact before downstream settlement is treated as justified.

Settlement / Receipt

Onchain value movement and the inspectable record that reconciles the outcome.

03 / What I built

The project spans the protocol model and the surfaces needed to actually use it.

The current implementation includes a persistent wallet-signed Runtime, Arc settlement contracts, EOA and EIP-1271 signing paths, direct and streaming settlement, relayed execution, indexed reads, and shared developer/agent surfaces.

Runtime

Workspace, Actor, Path, Intent, Proposal, Pact and Proof transitions with wallet-scoped authority and persistent storage.

Arc contracts

Explicit payer authorization, replay protection, USDC escrow, direct/streamed settlement and receipts.

SDK + CLI

Typed client access and dry-run-first command-line execution for payment flows.

REST + MCP

Shared application and agent surfaces for discovery, planning, preparation, validation, verification and safe reads.

Web application

A browser-facing path for connecting a wallet, creating Workspaces and exercising the settlement lifecycle.

04 / Technical decisions

The architecture keeps coordination authority separate from financial authority.

The Runtime can determine that a requested transition is allowed without becoming the thing that moves the money.

Signed coordination transition
        │
        ▼
Persistent Runtime
  evaluates authority + lifecycle state
        │
        ├── ALLOWED / COMMITTED / VERIFIED
        │
        └── BLOCKED + reason

Separate wallet authorization
        │
        ▼
Arc Hub / Vault
  verifies payer + replay state + funds
        │
        ▼
Onchain settlement receipt

This separation lets an agent or application participate in planning and lifecycle coordination without inheriting custody simply because it can call the Runtime.

Replay domains

The Hub also became the test bed for application-level two-dimensional nonce domains and later authorization-scoped lanes for deferred RailsCards. Those mechanisms are documented separately as research because the implementation pressure produced a reusable systems question.

06 / Boundary

What this evidence does—and does not—establish.

OpenRails has public testnet evidence for its delegated Workspace-to-settlement lifecycle. That does not establish production security, mainnet readiness, or that every surrounding Circle integration has been exercised end-to-end.

The persistent Runtime does not custody keys, sign for a wallet, broadcast financial transactions or become the source of truth for value movement. Arc transaction evidence and Vault state remain authoritative for settlement.
