The Programmable Relationship

What changes when value moves according to the state and authority of a relationship rather than as isolated transactions?

Question Working thesis Construction What it allows Boundary Derived investigations
01 / Question

A transaction tells us that value moved. It does not, by itself, preserve the authority, commitment, evidence, limits, recovery path, or history that made that movement legitimate.

transaction → consequence
relationship → authority → commitment → evidence → execution → receipt → continuation
02 / Working thesis

The relationship can be a first-class computational object. Transactions then become state transitions inside that object rather than the only durable thing the system remembers.

The useful object is not “Alice can send USDC.” It is closer to “this actor may perform this capability, for this purpose, under these limits, because these parties accepted these terms, until this state changes.”

03 / Construction
OpenRails interface shape — abridged from the current shared interface
const workspace = {
  ownerActorRef,
  status: "ACTIVE",
  provenance
};

const path = {
  workspaceRef: workspace.id,
  issuerActorRef,
  delegateActorRef,
  capabilities: ["PAY"],
  limits: [{
    asset: "USDC",
    maxAmount: "10000",
    maxAmountPerTransaction: "250",
    maxTransactionsPerPeriod: "100",
    periodSeconds: "3600",
    maxVelocityPerSecond: "50",
    maxLifespanSeconds: "86400"
  }],
  status: "ACTIVE",
  signatureBinding,
  provenance
};

The relationship context and the delegated authority are separate objects. That lets the runtime evaluate an action against persistent authority rather than treating possession of a key as sufficient permission.

Commitment is downstream of permission
const proposal = normalize(intent, path);
const decision = evaluate(proposal, path);

if (decision !== "ALLOW") {
  throw new Error("PACT_NOT_PERMITTED");
}

const pact = {
  workspaceRef,
  pathRef: path.id,
  proposalRef: proposal.id,
  decisionRef: decision.id,
  parties,
  paymentTerms,
  proofPolicy,
  status: "ACTIVE"
};

Path answers what may happen. Pact records what has now been committed to. A later payment can therefore retain both permission lineage and commitment lineage.

04 / What the construction allows
01Repeatable bounded authority

An agent can act repeatedly inside an established Path without receiving unrestricted custody or asking the principal to reconstruct the same permission for every action.

02Permission ≠ commitment

A broad delegation can authorize many possible actions while a Pact records the particular economic terms the parties actually accepted.

03Economic lineage

A receipt can be related back to the Workspace, Path, Proposal, decision, Pact, proof, and settlement that produced it.

04Relationship continuity

Failure or reconciliation does not have to erase the governing context; Gaia can open a case and attach rectification obligations to the same history.

Workspace→Path→Pact→Proof→Settlement→Receipt↺Relationship
05 / Boundary
This note does not claim that every economic relationship should live fully onchain.

The narrower claim is that systems gain useful guarantees when authority, commitments, evidence, execution state, and recovery remain explicitly related instead of being reconstructed after each transaction. OpenRails is one implementation path; Concord explores composition of multiple such relationships.
