01 / Pressure

Permission is broader than commitment.

A Path may authorize an agent to perform a class of actions. That does not mean every possible action inside that class has already been agreed.

Path:
agent may PAY up to 10,000 USDC
under these limits

≠

Pact:
these parties accepted
this exact 4,200 USDC economic action
under this proof policy

OpenRails therefore keeps delegation and commitment as separate objects instead of treating “authorized” as “already agreed.”

02 / Existing EVM substrate

A typed signature authenticates a message. It does not create a whole commercial lifecycle.

EIP-712 standardizes structured signing. It lets an application bind meaningful fields into a signature, but the application still decides what state transition that signature authorizes and how replay, lifecycle, evidence, and execution are handled.

Pact lives at that application layer. It is not a new signature scheme and not a new Ethereum transaction type. It records that a proposal which survived Path policy evaluation has become an active commitment inside the OpenRails Runtime.

03 / Construction

The commitment preserves its lineage.

type Pact = {
  workspaceRef: WorkspaceRef;
  pathRef: PathRef;
  proposalRef: ProposalRef;
  decisionRef: BaphometDecisionRef;

  parties: ActorRef[];
  paymentTerms: PaymentTerms;
  proofPolicy: ProofPolicy;

  status: "DRAFT" | "ACTIVE" | "REVOKED" | "EXPIRED";
  activatedAt?: string;

  signatureBinding: SignatureBinding;
  provenance: Provenance;
};

The Pact does not merely copy payment terms. It points back to the Workspace, delegated Path, normalized Proposal, and policy Decision that made the commitment admissible.

The proof policy can also state whether proof is required and exactly where in the later lifecycle it must appear: before authorization, claim, checkpoint settlement, or final settlement.

04 / Activation

A blocked proposal cannot become a Pact.

if (proposal.status !== "ALLOWED" ||
    decision.decision !== "ALLOW") {
  throw new RuntimeError(
    "POLICY_BLOCKED",
    "Pact signing requires an ALLOW Baphomet Decision."
  );
}

The Runtime then checks that the Decision refers to the same Proposal, input hash, policy version, and Pact reference.

assertReference(decision.proposalRef, proposal.id);

if (decision.inputHash !== proposal.inputHash)
  throw TERMS_MISMATCH;

if (decision.policyVersion !== proposal.policyVersion)
  throw POLICY_BLOCKED;

assertReference(decision.pactRef, pact.id);

The economic terms must remain unchanged across Intent, Proposal, and Pact:

if (!sameValue(pact.paymentTerms, intent.paymentTerms) ||
    !sameValue(pact.paymentTerms, proposal.normalizedTerms)) {
  throw new RuntimeError(
    "TERMS_MISMATCH",
    "Pact payment terms do not match the Intent and Proposal."
  );
}

Finally, the signer must be one of the Pact parties and the Path is checked again before the Pact moves from DRAFT to ACTIVE.

const signerActor = pact.parties
  .map(requireActor)
  .find(actor =>
    actor.walletAddress &&
    sameAddress(actor.walletAddress, binding.signer)
  );

if (!signerActor) throw AUTHORIZATION_REQUIRED;

const activatedPact = {
  ...pact,
  status: "ACTIVE",
  activatedAt: now
};
05 / What it allows

A later consequence can retain the commitment that produced it.

Workspace
   ↓
Path
   ↓
Intent
   ↓
Proposal
   ↓
ALLOW decision
   ↓
PACT
   ↓
Proof
   ↓
Settlement / Receipt

This makes it possible to distinguish several questions that a transaction alone cannot answer:

Path

Was this class of action within delegated authority?

Pact

Which exact economic terms did the parties commit to?

Proof

What evidence was required before a later transition?

Receipt

What economic consequence was actually observed?

06 / Boundary

Pact is not a legal-contract claim.

The accurate term is a machine-readable economic commitment inside OpenRails.

Whether a Pact has legal enforceability in a jurisdiction is a separate question and is not implied by the Runtime object. Likewise, activating a Pact does not mean money has moved: the Runtime response records the Pact commitment while transaction and financial effects remain separate.

permission ≠ commitment
commitment ≠ proof
commitment ≠ settlement
settlement ≠ legal enforceability

Invariant

No Pact from a BLOCK decision. Terms must stay consistent across Intent → Proposal → Pact.

Useful separation

  • delegation
  • proposal
  • policy decision
  • commitment
  • proof
  • financial execution
