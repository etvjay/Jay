Replay protection / concurrency

2D Nonce Lanes

What changes when replay protection is scoped to (account, lane) rather than one globally ordered sequence?

ImplementedEVM application layerNot an Ethereum replacement
Existing substrateConstructionWhy it helpsTrade-offsWhat it is not
01 / Existing substrate

Ethereum already has ordering.

An ordinary Ethereum account transaction nonce gives one signer one sequential ordering domain. That is useful precisely because it is simple: transactions from the same account cannot be replayed or arbitrarily reordered.

OpenRails does not replace that transaction nonce. The Hub adds a separate, contract-level replay domain for signed payment intents whose lifecycle can outlive the transaction that eventually submits them.

Ethereum transaction nonce

Protocol-level ordering for transactions from an account.

OpenRails Hub nonce

Application-level replay protection for signed economic authorizations consumed by a contract.

ERC-4337 also supports keyed nonce sequences, commonly described as a two-dimensional nonce model: a key selects a nonce domain and a sequence orders operations within that domain. The important point is therefore not that OpenRails discovered keyed nonces; it is what the application chooses those lanes to represent.

02 / Construction

The contract state is small.

mapping(address => mapping(uint256 => uint256))
    public accountNonceTracks;

function _consumeNonce(
    address account,
    uint256 channel,
    uint256 expectedNonce
) internal {
    require(
        accountNonceTracks[account][channel] == expectedNonce,
        "Nonce: invalid nonce"
    );

    accountNonceTracks[account][channel] = expectedNonce + 1;
}

The state key is effectively:

(signer, channel) -> nextExpectedNonce

The signed OpenRails settlement intent includes both `nonceChannel` and `nonceValue`, so a relayer cannot move a valid authorization to another lane without changing the signed message.

SettlementIntent(
  ...,
  uint256 nonceChannel,
  uint256 nonceValue
)

Execution therefore consumes only the referenced lane:

payer = recoverSigner(signedIntent);
_consumeNonce(payer, nonceChannel, nonceValue);
transferFrom(payer, hub, allocation);
03 / Why it helps here

Independent workloads stop contending on one sequence.

The OpenRails SDK contains a conventional lane allocator that maps task classes into persistent channels and advances a separate monotonic sequence for each `(account, channel)` pair.

public selectChannel(taskType: string): number {
  let hash = 5381;
  for (let i = 0; i < taskType.length; i++) {
    hash = ((hash << 5) + hash + taskType.charCodeAt(i)) | 0;
  }
  return Math.abs(hash) % 256;
}

public async nextNonce(account, channel) {
  const key = `nonce:${account.toLowerCase()}:${channel}`;
  const current = (await cache.get(key)) ?? 0;
  await cache.set(key, current + 1);
  return current;
}

This is useful when the application already knows that two classes of work should not block one another. For example, a persistent agent workload can maintain ordering within a lane while another independent workload advances elsewhere.

Single sequence

Easy to reason about, but unrelated work from the same authority contends on one ordering domain.

Multiple lanes

More concurrency, but the application must define and manage the lane semantics correctly.

04 / Trade-offs

More concurrency means more state and more policy.

A lane model moves complexity upward into the application. The system now has to decide who allocates channels, whether lanes are persistent or one-shot, how they are serialized, and whether any two actions actually should be independent.

It also creates more contract storage entries than a single global counter. That cost may be justified for high-concurrency delegated workflows and unnecessary for simple sequential payments.

05 / Boundary

This is not “better Ethereum nonces.”

It is a different replay-protection scope used inside a payment authorization protocol.

Ethereum's account nonce remains the transaction-ordering mechanism. ERC-4337 already provides keyed nonce semantics for account abstraction. OpenRails' contribution is application-specific: it binds lane selection to the semantics of economic authority and later uses a more specialized lane policy for deferred RailsCards.

That specialized policy is the next story.

Established terms

  • transaction nonce
  • keyed nonce
  • replay protection
  • nonce domain / lane
  • application-level authorization

Implementation evidence

`ArcOpenRailsHubV1` stores account × channel counters. The SDK includes a channelized `NonceEngine` for independent workloads.

Claim boundary

No claim that this model is universally superior, nor that OpenRails originated the general concept of keyed or 2D nonces.
