2D Nonce Lanes

A study of what changes when replay protection is scoped to an account and a lane instead of one account-wide application sequence.

SubstrateModelImplementationExecutionLimitsDerived question
01 / Existing substrate

The first nonce already exists below us.

Ethereum accounts already carry transaction nonces. Their job is protocol-level ordering and replay protection for transactions sent from an account. OpenRails does not replace or modify that mechanism.

A signed OpenRails payment authorization can exist before the transaction that eventually submits it. That creates a second replay problem at the application layer: the contract needs to know whether a particular signed authorization has already been consumed.

ERC-4337 also provides keyed nonce sequences for smart-account operations. The useful comparison is therefore not “one-dimensional Ethereum versus two-dimensional OpenRails.” Ethereum account transactions, ERC-4337 user operations, and OpenRails payment authorizations sit at different layers and protect different objects.

Layer model
Ethereum account
    transaction nonce
        │
        └── orders protocol transactions from an account

ERC-4337 smart account
    nonce key + sequence
        │
        └── orders UserOperations inside account-defined nonce domains

OpenRails Hub
    signer + channel + sequence
        │
        └── consumes signed payment authorizations at the application layer
02 / Model

The state is a map of independent sequences.

Instead of one application counter per signer, OpenRails stores one counter for each signer and channel pair.

State model
N[account][channel] = next expected application nonce

Account A
    lane 0   → 17
    lane 1   →  4
    lane 7   → 92

Account B
    lane 0   →  3
    lane 7   → 11

Executing an authorization in `A / lane 7` changes only that sequence. It does not advance `A / lane 0`, `A / lane 1`, or any lane owned by Account B.

This is the basic concurrency property. Whether it is useful depends entirely on what the application chooses a lane to mean.

03 / Implementation

The Solidity mechanism is deliberately small.

mapping(address => mapping(uint256 => uint256))
    public accountNonceTracks;

function _consumeNonce(
    address account,
    uint256 channel,
    uint256 expectedNonce
) internal {
    require(
        accountNonceTracks[account][channel] == expectedNonce,
        "Nonce: invalid nonce"
    );

    accountNonceTracks[account][channel] = expectedNonce + 1;
}

The lane and sequence are part of the EIP-712 settlement intent itself.

SettlementIntent(
  bytes32 paycardId,
  bytes32 metadataHash,
  address recipient,
  uint256 totalAllocationPool,
  uint256 flowVelocityPerSecond,
  uint256 genesisTimestamp,
  uint256 lifespanSeconds,
  address residualDeltaRecipient,
  uint256 nonceChannel,
  uint256 nonceValue
)

That matters because the relayer cannot take a valid signed intent from one lane and submit it under another without changing the signed message.

04 / Execution trace

Ordering exists inside a lane, not across every lane.

Example
Initial state

N[A][payments] = 12
N[A][streams]  = 31

Authorization P
    account = A
    lane    = payments
    nonce   = 12

Authorization S
    account = A
    lane    = streams
    nonce   = 31

execute(S)
    N[A][streams]  = 32
    N[A][payments] = 12

execute(P)
    N[A][payments] = 13

replay(P, nonce=12)
    rejected

The SDK includes a conventional channel allocator for this persistent-lane interpretation: a workload descriptor is mapped to a channel and each account/channel pair advances independently.

public selectChannel(taskType: string): number {
  let hash = 5381;
  for (let i = 0; i < taskType.length; i++) {
    hash = ((hash << 5) + hash + taskType.charCodeAt(i)) | 0;
  }
  return Math.abs(hash) % 256;
}

The point is not that hashing a task name is inherently special. It demonstrates the conventional interpretation: the channel identifies a continuing class of work, and the nonce sequences operations inside that class.

05 / Limits

Partitioning the nonce space does not remove ordering problems. It relocates them.

The application now has to define which operations belong together, which operations may safely commute, how channels are allocated, and how much persistent state the contract should accumulate.

A single application nonce is easier to inspect and reason about. Multiple nonce domains are useful only when the independence is real enough to justify the extra namespace and state.

This also should not be presented as a general alternative to ERC-4337 keyed nonces. ERC-4337 already provides nonce-key semantics for UserOperations. OpenRails uses a similar dimensional idea at a separate protocol boundary: signed economic authorizations consumed by the Hub.

06 / Derived question

What should a lane represent?

The initial answer was a persistent execution domain. RailsCard exposed a case where that was still too coarse.

Two deferred authorizations may be issued by the same account, serve the same payment class, and still have no ordering dependency between them. That failure produced the next experiment: allocate the lane to the authorization itself.

Established vocabulary

  • transaction nonce
  • keyed nonce
  • sequence
  • replay protection
  • application-level authorization

Implementation

`ArcOpenRailsHubV1` stores account × channel counters. `NonceEngine` maintains corresponding independent sequences client-side.

Claim boundary

No claim that OpenRails originated keyed nonce domains or that multiple lanes are preferable for every workload.
