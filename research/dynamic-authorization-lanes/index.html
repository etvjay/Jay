Dynamic Authorization Lanes

A nonce-lane policy in which the lane is allocated to one independently exercisable authorization rather than to a persistent execution queue.

ImplementedFresh uint128 laneReverse-order redemption tested
FailureLineageModelCodeEvidenceLimits
01 / Failure that produced the mechanism

Replay protection was correct. The authority model was not.

RailsCards can be signed before they are redeemed. Two independently valid cards could therefore exist at the same time.

The early flow issued both against the same current nonce on channel `0`. Whichever card was redeemed first consumed that nonce and made the other card stale.

Failure trace
N[payer][0] = 12

sign Card A
    lane  = 0
    nonce = 12

sign Card B
    lane  = 0
    nonce = 12

redeem B
    N[payer][0] = 13

redeem A
    expected 12
    observed 13
    → rejected

The rejection is correct replay behavior. The problem is that A and B were never meant to be ordered relative to one another.

02 / Technical lineage

The mechanism starts from ordinary keyed nonce semantics.

Ethereum account transactions use a sequential account nonce. ERC-4337 allows smart accounts to partition UserOperation nonces into keyed sequences. OpenRails already had its own persistent `(account, channel) → sequence` application nonce model.

The RailsCard change is therefore not “invent a second dimension.” The change is narrower: change what chooses the key and how long that key is expected to live.

Semantic difference
Persistent keyed lane

    key = task class / module / session / queue

    N[account][key]
        0 → 1 → 2 → 3 → ...


Authorization-scoped lane

    key = this deferred authority

    N[account][key]
        0 → 1

    another authority receives another key

The underlying storage model is the same kind of two-dimensional counter. The research question is about the semantics of namespace allocation.

03 / Model

The replay domain is created with the authority.

For a deferred RailsCard, OpenRails allocates a fresh non-zero 128-bit channel. Channel `0` remains reserved for immediate sequential opens.

Authorization model
Card A
    signed terms
    + lane α
    + nonce 0

Card B
    signed terms
    + lane β
    + nonce 0

α ≠ β

consume(A)
    N[payer][α] : 0 → 1

consume(B)
    N[payer][β] : 0 → 1

The lane becomes one of the coordinates that define where this authorization may be consumed.

Because `nonceChannel` and `nonceValue` are inside the signed settlement intent, a relayer cannot re-home an authorization into another replay domain without invalidating the signature.

04 / Code

Fresh lane allocation is explicit.

export const RAILSCARD_NONCE_CHANNEL_BYTES = 16;

export function nonceChannelFromBytes(
  bytes: Uint8Array
): bigint {
  let channel = 0n;

  for (const byte of bytes) {
    channel = (channel << 8n) | BigInt(byte);
  }

  // channel 0 is reserved for immediate sequential opens
  return channel === 0n ? 1n : channel;
}

export function randomRailsCardNonceChannel(): bigint {
  const bytes = new Uint8Array(16);
  crypto.getRandomValues(bytes);
  return nonceChannelFromBytes(bytes);
}

The application checks the generated lane against current Hub state before signing the card.

for (let attempt = 0; attempt < MAX_ATTEMPTS; attempt += 1) {
  const candidate = randomRailsCardNonceChannel();

  const currentNonce = await hub.accountNonceTracks(
    payer,
    candidate
  );

  if (currentNonce === 0n) {
    return candidate;
  }
}

The contract itself needs no special RailsCard-specific nonce primitive. It still consumes the same `(payer, channel, nonce)` state. The innovation, if the term is useful here, is entirely in allocation policy.

05 / Test evidence

The test is about independence, not throughput.

The merged RailsCard tests construct two recipient-bound cards on different lanes, sign both before either is used, then redeem them in reverse order. The same test shape is repeated for bearer cards.

const channelA = 41_001;
const channelB = 41_002;

const envelopeA = await sign(
  intent("bound-a", channelA, recipientA)
);

const envelopeB = await sign(
  intent("bound-b", channelB, recipientB)
);

await openFixed(envelopeB);
await openFixed(envelopeA);

expect(
  await hub.accountNonceTracks(payer, channelA)
).to.equal(1n);

expect(
  await hub.accountNonceTracks(payer, channelB)
).to.equal(1n);

A subsequent authorization attempting to reuse `channelA` with nonce `0` is rejected. The evidence therefore supports a deliberately narrow claim:

What survived the experiment
two deferred authorizations
    same issuer
    no intended ordering dependency

        ↓

separate replay domains

        ↓

redeem in either order
while replay on either consumed domain still fails
06 / Limits and open questions

Independence has a storage and namespace cost.

Each fresh lane can create another `(payer, lane)` storage entry. For immediate sequential payments this would be unnecessary, which is why channel `0` remains the simple path.

The allocator uses randomness plus an unused-lane read. A deterministic channel derived from an authorization identifier is another plausible design, but it would have different collision, predictability, and linkage properties and has not been established as preferable here.

The mechanism also does not resolve EIP-2612 permit concurrency. Token permit state and OpenRails Hub replay state are separate authorization surfaces.

Finally, describing a one-shot lane as a “nullifier” would be too strong. The `0 → 1` spent-state behavior is analogous at a high level, but OpenRails is not constructing a cryptographic or zero-knowledge nullifier.

Precise term

Authorization-scoped replay domain.

Implementation status

Merged in RailsCard nonce-isolation work; recipient-bound and bearer reverse-order redemption tests included.

Not claimed

  • not a replacement for ERC-4337
  • not universally cheaper
  • not a ZK nullifier
  • not a permit-concurrency solution
