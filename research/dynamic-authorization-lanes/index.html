Dynamic Authorization Lanes

When a nonce lane stops meaning “this queue” and instead identifies one independently exercisable authorization.

ImplementedFresh uint128 lanesReverse-order redemption tested
PressureExisting modelsConstructionResultTrade-offsBoundary
01 / Pressure

Two valid promises were accidentally competing for one slot.

A deferred RailsCard can be signed now and redeemed later. The early implementation put every outstanding card on the same sequential lane.

// both cards are prepared before either is redeemed
Card A -> (channel = 0, nonce = 12)
Card B -> (channel = 0, nonce = 12)

redeem(B)
// channel 0 becomes 13

redeem(A)
// fails: A still carries nonce 12

The replay protection worked. The concurrency semantics did not. Independent authorizations became mutually exclusive because they shared an ordering position.

02 / Existing models

The novelty is not the existence of a nonce key.

Ethereum account transactions already use a sequential nonce. ERC-4337 defines keyed nonce sequences, allowing a smart account to maintain independent ordering domains. OpenRails itself also has a conventional `NonceEngine` that maps workload classes into persistent channels.

The RailsCard experiment changes something narrower: the allocation policy and semantic lifetime of the lane.

Persistent keyed lane

A lane usually represents a module, session, task class, queue, or continuing ordering domain. Its sequence may advance many times.

Authorization-scoped lane

A fresh lane is allocated to one deferred authorization. For the demonstrated RailsCard flow, it is effectively consumed from nonce 0 to nonce 1.

03 / Construction

Allocate the replay domain when the authority is created.

export const RAILSCARD_NONCE_CHANNEL_BYTES = 16;

export function randomRailsCardNonceChannel(): bigint {
  const bytes = new Uint8Array(16);
  crypto.getRandomValues(bytes);

  let channel = 0n;
  for (const byte of bytes) {
    channel = (channel << 8n) | BigInt(byte);
  }

  // channel 0 stays reserved for immediate sequential opens
  return channel === 0n ? 1n : channel;
}

Before signing, the application checks that the candidate lane is unused on the Hub. The card is then signed with that lane and `nonceValue = 0`.

for (let attempt = 0; attempt < MAX_ATTEMPTS; attempt++) {
  const candidate = randomRailsCardNonceChannel();

  const currentNonce = await hub.accountNonceTracks(
    payer,
    candidate
  );

  if (currentNonce === 0n) return candidate;
}

The signed settlement intent commits to the lane:

SettlementIntent(
  paycardId,
  metadataHash,
  recipient,
  allocation,
  velocity,
  genesis,
  lifespan,
  recovery,
  nonceChannel,
  nonceValue
)

So the lane is not just transport metadata. Moving a card to another lane changes the signed message.

04 / Result

Redemption order stops creating an artificial dependency.

Card A -> lane 41001, nonce 0
Card B -> lane 41002, nonce 0

redeem(B)
// N[payer][41002] = 1

redeem(A)
// N[payer][41001] = 1

replay(A on 41001, nonce 0)
// rejected

The test suite covers both recipient-bound and bearer RailsCards, signs two cards in advance, redeems them in reverse order, then confirms replay on a consumed lane fails.

The result is modest but useful: authorization independence + replay protection + arbitrary redemption order for the tested deferred-card flow.

05 / Trade-offs

The lane count grows with outstanding authorizations.

This policy creates additional contract state because each fresh authorization touches a new `(payer, lane)` mapping entry. The current allocator also relies on random lane generation plus an onchain unused-lane check. A deterministic derivation from authorization identity could be studied, but would change collision and privacy properties.

For simple immediate payments, a fresh lane per authorization is unnecessary. OpenRails explicitly keeps channel `0` for sequential immediate opens.

There is also a separate authorization-concurrency problem around EIP-2612 permits. The RailsCard lane fix does not solve that problem and should not be described as if it does.

06 / Boundary

The lane is best understood as part of the authority.

This is not a claim that per-authorization lanes should replace persistent keyed nonces.

It is a specific policy for deferred economic authorizations whose exercise should be independent. ERC-4337 already permits arbitrary nonce keys; the OpenRails distinction is semantic: the lane is allocated to the authorization instance itself rather than primarily to a persistent execution queue.

A useful description is therefore:

Dynamic Authorization Lane
=
a fresh replay namespace
allocated to one independently exercisable authority

For one-shot RailsCards, the lane behaves somewhat like a spent-state coordinate: `0 -> 1`. That is only an analogy. OpenRails does not implement a cryptographic or ZK nullifier system.

Pressure

Multiple deferred cards signed before redemption all reused `(channel 0, currentNonce)`, so first redemption invalidated the others.

Surviving claim

Independent deferred authorizations can use independent replay domains and still reject replay.

Not claimed

  • not a replacement for ERC-4337
  • not universally lower-cost
  • not a ZK nullifier
  • not a solution to permit concurrency
