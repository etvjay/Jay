Path

How can an actor repeatedly exercise another party’s economic authority without receiving unrestricted custody?

01 / Pressure

Repeated autonomy creates an authority problem.

A service or agent may need to perform many economic actions. Asking the principal to re-authorize every action preserves control but removes useful autonomy. Giving the actor an unrestricted key preserves autonomy but expands the blast radius.

// repeated explicit approval
request 1 -> principal signs
request 2 -> principal signs
request 3 -> principal signs

// unrestricted custody
agent gets wallet authority
agent can act outside the intended objective

Path explores a middle object: establish a bounded delegation once, then evaluate subsequent actions against that persistent authority.

02 / Existing EVM substrate

A signature, an allowance and a delegation are not the same thing.

EIP-712 gives applications a standard way to sign typed structured data. It does not define what authority the signed object should represent, nor does it provide replay protection by itself.

ERC-20 approve gives a spender an amount-denominated token allowance. That is useful token-level authority, but it does not natively encode a business purpose, transaction frequency, stream velocity, workspace identity, or a broader economic lifecycle.

ERC-4337 smart accounts can implement custom validation logic for UserOperations. Path does not replace that account-level validation. It sits at a different semantic layer: an OpenRails Runtime decides whether an economic proposal is permitted by an application-level delegation before later wallet or settlement execution.

ERC-20 allowance

“spender may withdraw up to this token amount.”

OpenRails Path

“this delegate may perform these capabilities, on these resources, under these quantitative and temporal bounds.”

03 / Construction

The delegation is a first-class object.

type Path = {
  workspaceRef: WorkspaceRef;
  issuerActorRef: ActorRef;
  delegateActorRef: ActorRef;

  capabilities: string[];
  resourceRefs?: PathResourceRef[];
  limits: PathLimit[];

  status:
    | "PREPARED"
    | "ACTIVE"
    | "REVOKED"
    | "EXPIRED";

  signatureBinding: SignatureBinding;
  provenance: Provenance;
};

Each asset limit can express more than one ceiling:

type PathLimit = {
  asset: Asset;

  maxAmount: string;
  maxAmountPerTransaction?: string;

  maxTransactionsPerPeriod: string;
  periodSeconds: string;

  maxVelocityPerSecond?: string;
  maxLifespanSeconds?: string;
};

The important distinction is that these fields describe the authority relationship itself. They are not inferred after an action is submitted.

04 / Runtime enforcement

The Workspace authority must activate and can revoke the Path.

const workspace = requireWorkspace(state, path.workspaceRef.id);
const authority = requireWorkspaceAuthority(state, workspace.id);
const issuer = requireActor(state, path.issuerActorRef.id);
const delegate = requireActor(state, path.delegateActorRef.id);

if (path.status !== "PREPARED") {
  throw new RuntimeError("STATE_STALE", ...);
}

if (!issuer.walletAddress ||
    issuer.walletAddress !== authority ||
    binding.signer !== authority) {
  throw new RuntimeError(
    "AUTHORIZATION_REQUIRED",
    "Path activation signer is not the Workspace authority."
  );
}

Once active, proposals are checked against the applicable limits. A single transaction can be blocked for exceeding the per-transaction or overall limit:

if (amount > limit.maxAmount) {
  throw POLICY_BLOCKED;
}

if (limit.maxAmountPerTransaction !== undefined &&
    amount > limit.maxAmountPerTransaction) {
  throw POLICY_BLOCKED;
}

Streamed settlement adds velocity and lifespan constraints:

if (terms.settlementShape === "streamed") {
  if (velocity > limit.maxVelocityPerSecond) {
    throw POLICY_BLOCKED;
  }

  if (lifespan > limit.maxLifespanSeconds) {
    throw POLICY_BLOCKED;
  }
}

The Runtime also keeps period usage. Transaction count and cumulative amount are advanced in a bounded bucket:

nextCount = usage.transactionCount + 1;
nextAmount = usage.amount + terms.amount;

if (nextCount > limit.maxTransactionsPerPeriod) {
  throw POLICY_BLOCKED;
}

if (nextAmount > limit.maxAmount) {
  throw POLICY_BLOCKED;
}

When evaluation fails, the resulting decision records PATH_LIMIT_EXCEEDED and explicitly states that no wallet action, Paycard creation, or value movement occurred.

The principal does not have to reconstruct the same delegation for every request, while the delegate still cannot treat “I was authorized once” as unlimited future authority.

This becomes especially useful when agents operate continuously: authority can persist longer than one action while remaining narrower than ownership of the underlying wallet.

06 / Trade-offs

The runtime becomes part of the trust and availability boundary.

Path limits only matter if every delegated proposal that depends on them actually passes through the enforcing Runtime. A parallel execution route that bypasses the Path is outside this guarantee.

Period buckets, resource references, status transitions, authenticated ingestion and provenance also add state and implementation complexity. A simple ERC-20 allowance may be preferable when the only intended policy really is “spender may move at most X tokens.”

Path is stronger when

authority needs purpose, capability, frequency, streaming or lifecycle bounds across many actions.

Simpler primitives are stronger when

the policy is only a token amount ceiling and extra runtime semantics would add little value.

07 / Terminology boundary

Path is application-level delegated authority.

It is not a new EVM permission primitive, not an ERC-20 replacement, and not itself a smart-account validation standard.

The most accurate description is a persistent bounded delegation object enforced by the OpenRails Runtime. EIP-712 provides the typed-signature substrate; wallet/account systems remain responsible for cryptographic execution authority; settlement contracts remain authoritative for actual value movement.

Path answers:
"What may this delegate repeatedly do?"
