Workspace

If humans, applications, services and agents participate in one continuing economic activity, where should the shared context live?

01 / Pressure

A wallet can sign. It does not describe the whole activity.

A persistent commercial workflow may involve a person, an agent, an application, a service and several delegated relationships. Reconstructing that context from isolated addresses and transactions makes later authorization and provenance harder to reason about.

02 / Construction

The Workspace is separate from the actors inside it.

type Workspace = {
  id: string;
  name: string;
  ownerActorRef: ActorRef;
  status: "DRAFT" | "ACTIVE" | "SUSPENDED" | "CLOSED";
  createdAt: string;
  updatedAt: string;
  provenance: Provenance;
};

type Actor = {
  id: string;
  kind: "person" | "application" | "agent" | "service" | "sidecar";
  authorityStatus:
    | "UNVERIFIED"
    | "VERIFIED"
    | "SUSPENDED"
    | "REVOKED";
  walletAddress?: string;
};

type WorkspaceMember = {
  workspaceRef: WorkspaceRef;
  actorRef: ActorRef;
  role: "owner" | "administrator" | "operator" | "member" | "observer";
  permissions?: string[];
};

This lets identity, membership and cryptographic authority remain related without treating them as one field.

03 / Authority binding

Registration persists the object and its authenticated Runtime authority.

private prepareWorkspace(request, binding, state, at) {
  const workspace = request.data.workspace;

  if (state.workspaces[workspace.id] ||
      state.workspaceAuthorities[workspace.id]) {
    throw STATE_STALE;
  }

  const authority = getAddress(binding.signer);

  return {
    commit: draft => {
      draft.workspaces[workspace.id] = clone(workspace);
      draft.workspaceAuthorities[workspace.id] = authority;
    }
  };
}

The Runtime therefore has two related facts: the Workspace’s owner actor reference and the authenticated wallet authority that registered the context.

interface RuntimeState {
  workspaces: Record<string, Workspace>;
  workspaceAuthorities: Record<string, string>;
  actors: Record<string, Actor>;
  actorWorkspaces: Record<string, string>;

  paths: Record<string, Path>;
  intents: Record<string, Intent>;
  proposals: Record<string, Proposal>;
  pacts: Record<string, Pact>;
  proofs: Record<string, Proof>;
}
04 / What it allows

Downstream state shares a common provenance root.

Wallet ≠ activity

A signer can authorize transitions without being the only identity or organizational context the system remembers.

Heterogeneous actors

People, agents, applications and services can occupy different roles inside one continuing context.

Shared lineage

Paths, Intents, Proposals and Pacts can all point back to the same Workspace.

Lifecycle

The context can be suspended or closed independently of any single transaction.

Workspace
├── Actors
├── Paths
├── Intents
├── Proposals
├── Pacts
└── Proof / receipt lineage
05 / Boundary

Workspace is not a custody container or account-abstraction standard.

It is an application-level coordination and authority context.

Wallets and account systems still provide cryptographic authorization. Settlement contracts and chain state remain authoritative for actual value movement. Workspace provides the durable context in which those later actions can be interpreted.

Actor kinds

  • person
  • application
  • agent
  • service
  • sidecar

Core distinction

Cryptographic authority is necessary, but it is not the same object as persistent organizational or economic context.
